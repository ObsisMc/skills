# Template: docs/decisions/README.md

A decision-record convention for repositories that agents work in. A record is **the design document** for one decision: while proposed and accepted it carries the full design and the rollout plan, so a reviewer can judge it without reading code and an agent can implement it without asking; once implemented it states what the system promises. Its core — the decision drivers, the invariants and the considered options — is frozen once accepted; the decision is changed only by superseding it. The evidence behind this shape is in `references/landscape.md` §6. The README is the whole convention; the `verify-decision-*` gates in `references/gates.md` enforce it.

The folder is flat: status lives in the record's header, not in a lifecycle folder. Folders cannot express partial supersession or two-way links, and moving files on every status change breaks links.

```markdown
# Decisions

A decision record holds **why this choice and what it beat**, and **how it is built**: while it is proposed it is the complete design and plan for the work; once implemented it states what the system promises. Agents start every session without memory; without these records they re-propose rejected designs, "clean up" code that is odd on purpose, or stall on questions the design already answered.

What holds across the whole system *today* is summarized in [architecture.md → Current decisions](../architecture.md#current-decisions). Module contracts live in module READMEs; measurements and test evidence live in <<evidence location, e.g. docs/validation/>>; progress lives in issues and PRs.

Postmortems are the other kind of record and live in [../postmortem/](../postmortem/README.md): a decision looks forward (we chose A), a postmortem looks back (a bug escaped and here is why every net missed it).

## Principles

1. One record, one decision. Independent choices that can be reviewed separately become items D1, D2, … inside it.
2. Once accepted, the decision stands: *Decision drivers*, *Invariants* and *Considered options* are frozen. After implementation the facts in *Decision* (paths, table names, configuration keys) are kept in sync with the code. A changed decision is a new record that supersedes the old one.
3. While proposed, write it to the point where a reviewer can judge the design without reading code and an implementer can build it without asking: data model, flows, interfaces and configuration all belong in it. Once implemented, plans and speculation are removed; only the system's promises remain.
4. Progress belongs in issues and PRs, not in the record.
5. Every rule here that a script can check, a script checks.

## When to write one

Write a record when work involves any of:

- choosing A over a plausible B (library, pattern, data layout, protocol);
- deliberately *not* doing something an obvious reading of the code would expect;
- adding or removing an abstraction, owner, or module boundary;
- accepting a limitation a future reader will want to reverse;
- a feature that needs a design before anyone can start (sign-in, sharing, a sync protocol);
- a major-version upgrade that changes behavior.

Not for: configuration values, minor upgrades, or a fix that has one correct form.

A record that needs sign-off starts in its own PR as `proposed` and becomes `accepted` in the PR that merges it. A small decision that only appears during implementation goes in the same PR as the code.

## File name and references

- `YYYY-MM-DD-<slug>.md` — the date the record was first written, then a kebab-case slug. The slug is unique across all records and is how records are cited (`single-writer-store`), in text, relations and test tags.
- No sequence numbers: two branches each adding "the next number" collide on merge.

## Status and lifecycle

| Status | Meaning | How the body may change |
| --- | --- | --- |
| proposed | Under review | Freely |
| accepted | In force; build to it | *Decision drivers*, *Invariants*, *Considered options* are frozen; the other sections may be corrected as implementation proceeds (rollout, how an open question was settled) |
| implemented | Built and verified | On entering: delete *Rollout* and *Acceptance criteria* and stale speculation, rewrite in the present tense, add *Verification*. Afterwards the facts in *Decision* follow the code. The three frozen sections stay frozen |
| rejected | Considered and declined | Frozen; kept so the same idea is not re-proposed |
| deprecated | No longer applies and nothing replaces it | Frozen; add one dated line at the top saying why |
| superseded | Wholly replaced by another record | Frozen |

When the implementation departs from an accepted record: a difference in detail (how files are split, a configuration name) is written into *Decision* with the reason when the record becomes `implemented`; breaking an invariant or changing the decision needs a new record that supersedes it, wholly or in part.

Changing a frozen section needs the `decision-amend` PR label and a reason in the PR (`verify-decision-immutable`).

## Template

Copy this to start a record. `proposed` and `accepted` records use this structure:

```markdown
# <the decision, as a declarative sentence>

- Status: proposed
- Date: YYYY-MM-DD
- Deciders: <names>
- Scope: <one of the scopes below>
- Relations: none

One opening paragraph: the final design, the key behavior, what it affects, and what this record does not cover.

## Context and problem

The problem and its constraints, readable without the solution.

## Decision drivers

1. <goal or constraint, numbered so later sections can cite it>

## Decision

### D1: <the rule, as a declarative sentence>

State the rule and its externally visible behavior first, then why (constraints, failure modes, cost).
Where it is easy to misread, give the boundary or a counter-example (a table or a short code block).
Data model, flows, interfaces and configuration go in the D they belong to, or in their own subsection under Decision.

## Failure and recovery

(When the decision involves state, transactions or external side effects.) The outcome of each failure and how the system recovers.

## Invariants

1. <a short, positive promise the system keeps, verifiable on its own>

## Considered options

| Option | Strengths | Why rejected |
| --- | --- | --- |
| **Option A** | Where it is genuinely better | Which decision drivers it loses on, by number |

## Risks and costs

## Open questions

(Optional.) Only boundaries deliberately left for later, each with the default an implementation follows.

## Rollout

Phases; for each, its scope, its done condition and the behavior that changes from then on.
For autonomous implementation by an agent, add an *Autonomous implementation agreement* here (see below).

## Acceptance criteria

The observable state that means done, and which kind of test verifies each invariant.

## More information

- Revisit when: <the condition that reopens this decision>
- Evidence: <links to spikes, measurements, discussions>
```

When the record becomes `implemented`, delete *Rollout* and *Acceptance criteria* and add, before *More information*:

```markdown
## Verification

Which kind of test or check guarantees each invariant (in words, never file paths).
```

Required sections, for every status: *Context and problem*, *Decision drivers*, *Decision* (with at least `### D1`), *Invariants* (numbered 1, 2, 3 …), *Considered options* (a table with a *Strengths* column), *Risks and costs*, *More information* (with a non-empty *Revisit when*). `proposed` and `accepted` also require *Rollout* and *Acceptance criteria* and forbid *Verification*; `implemented` requires *Verification* and forbids *Rollout* and *Acceptance criteria*. *Failure and recovery* and *Open questions* are optional. `verify-decision-format` checks exactly this list.

How to write it:

- **Conclusion first, then its boundaries**: the opening paragraph alone says what is decided and what is out of scope.
- **Every D answers why** — especially where data comes from, identity boundaries, what is persisted and how errors are handled.
- **Invariants** are short, positive system promises, not implementation steps or aspirations. A test that verifies one carries `[decision:<slug>#<n>]` in its title.
- **Considered options** concede what each option does better; the rejection cites decision drivers, not just "too complex".
- **Enough detail** means a reviewer can judge the design without reading code, and an implementer can build it without asking.
- *Rollout*, *Acceptance criteria* and *Open questions* only matter before implementation; they are deleted or rewritten when the record becomes `implemented`.

### Autonomous implementation agreement

A `Rollout` subsection that lets an agent implement an accepted record without stopping for approval at every step:

- **Pre-approved**: the dependencies (with exact versions) and schema migrations this record lists. Only what is listed; anything else is still "ask first".
- **Agent's latitude**: decisions the agent may make on its own (file layout, naming, test structure, internal helpers).
- **Stop and ask when**: an invariant cannot be kept, the design is found wrong, a dependency or migration not listed is needed, or <<repo-specific conditions>>.
- **PR organization**: how many PRs, how commits are split, who merges.

Scopes: <<the scope list from the interview, e.g. domain, storage, auth, toolchain>>. A new scope is added here and in the gate's configuration in the same PR.

## Relations

*Relations* is a list separated by `; `, each item one of (`<ref>` is a slug, or `ADR-NNNN` for a legacy record), or `none`:

- `depends on <ref>`
- `supersedes <ref>`, or `supersedes <ref>: <which part>` for part of it
- `superseded by <ref>` (status `superseded`), or `<which part> superseded by <ref>` (status unchanged)

Both sides of a supersession are written; `verify-decision-format` checks that they agree. A superseded or deprecated record may not appear in *Current decisions*.

## Implementation status

A test or verify script that verifies invariant *n* of a record carries `[decision:<slug>#<n>]` in its title. The index counts covered invariants per record. Records never link to tests, so renaming or moving a test changes nothing here; deleting the last test for an invariant lowers the count in that PR's generated index, where review sees it. `verify-decision-tags` rejects tags that name no record or no invariant. Tests under <<prototype or spike directories>> do not count: a spike shows a decision is feasible, not that the product implements it.

- A module README's *Decisions* section lists the records that shape it, by slug; its *Invariants* restate the record invariants it must uphold and link the record.

## Notes for the generator

- Do not write decision records during initialization unless the survey surfaced a decision the user confirms (e.g. "we deliberately don't use an ORM"). An empty, well-formed folder with an empty generated index is the correct starting state.
- Write the README in the language the user writes decisions in. The *Status and lifecycle* table and the *Required sections* paragraph are the gate's configuration source: header field names, status values, required and forbidden headings per status, the frozen sections and the relation keywords in the `verify-decision-*` scripts must match them word for word. Translate them only together with that configuration.
- The *Autonomous implementation agreement* is on by default: keep the subsection in the template. Its two limits are fixed — only the dependencies and migrations a record lists are pre-approved, and the record's *Stop and ask when* conditions still stop the agent. Add the matching exception to the "Ask first" line in `AGENTS.md` (`templates/AGENTS.md`). Leave it out only if the user declines it in the interview.
- If the repo already has decision records (`docs/adr/`, `docs/architecture/decisions/`, MADR files): keep their directory, freeze their bodies, keep their names, and migrate only their headers to the five fields — one PR with the `decision-amend` label, the old status text kept as a quoted note. Records written after that point use dated names and this format. Tell the user which existing records already supersede each other and write those relations.
- Add the *Current decisions* section to `docs/architecture.md` at the same time (`templates/architecture.md`).
- The generated index needs markers the generator replaces between; keep them when editing the README.
