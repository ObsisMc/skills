# Template: docs/decisions/README.md

A decision-record convention for repositories that agents work in. The body format follows [MADR 4.0](https://adr.github.io/madr/); the lifecycle follows the proposal processes of large projects — a record is frozen once accepted and changed only by superseding it (Rust RFCs, Python PEPs). The evidence is in `references/landscape.md` §6. The README is the whole convention; the `verify-decision-*` gates in `references/gates.md` enforce it.

The folder is flat: status lives in the record's header, not in a lifecycle folder. Folders cannot express partial supersession or two-way links, and moving files on every status change breaks links.

# Decisions

A decision record answers one question: **why this choice, and what it beat.** Agents start every session without memory; without these records they re-propose rejected designs and "clean up" code that is odd on purpose.

What holds *today* is not read from here: [architecture.md → Current decisions](../architecture.md#current-decisions) lists the decision in force for each scope and links the record behind it. Module contracts live in module READMEs; measurements and test evidence live in <<evidence location, e.g. docs/validation/>>.

Postmortems are the other kind of record and live in [../postmortem/](../postmortem/README.md): a decision looks forward (we chose A), a postmortem looks back (a bug escaped and here is why every net missed it).

## Principles

1. One record, one decision.
2. An accepted record's body is frozen; a changed decision is a new record that supersedes it.
3. A record holds nothing that drifts: no configuration values, version pins, test paths or measurements — each has a home listed at the end.
4. Every rule here that a script can check, a script checks.

## When to write one

Write a record when a change involves any of:

- choosing A over a plausible B (library, pattern, data layout, protocol);
- deliberately *not* doing something an obvious reading of the code would expect;
- adding or removing an abstraction, owner, or module boundary;
- accepting a limitation a future reader will want to reverse;
- a major-version upgrade that changes behavior.

Not for: configuration values, minor upgrades, implementation details, or a fix that has one correct form.

Two cadences. A decision that needs sign-off before work starts gets its own PR with status `proposed`. A decision that comes up during implementation goes in the same PR as the code.

The test: *if another agent saw this code in three months, would they ask "why not B?"* If yes, write it.

## File name and references

- `YYYY-MM-DD-<slug>.md` — the date the record was first written, then a kebab-case slug. The slug is unique across all records and is how records are cited (`single-writer-store`), in text, relations and test tags.
- No sequence numbers: two branches each adding "the next number" collide on merge.
<<If the repo already had numbered records: "Records `0001`–`<<NNNN>>` predate this convention; they keep their names and bodies, are cited as `ADR-NNNN`, and only their headers follow the format below.">>

## Template

```markdown
# <the decision, as a declarative sentence>

- Status: proposed
- Date: YYYY-MM-DD
- Deciders: <names>
- Scope: <one of the scopes below>
- Relations: none

## Context and problem

The problem and its constraints, readable without the solution.

## Decision drivers

1. <goal or constraint, numbered so options can cite it>

## Considered options

- **Option A** — how it fares against the drivers.
- **Option B** — which drivers it loses on, and why.

## Decision outcome

Chosen: option A, <one-sentence conclusion>.

- <what is chosen and where its boundaries are>

### Constraints

1. <a rule this decision makes permanently true>

### Consequences

What it buys, what it costs, what could go wrong.

### Confirmation

- Constraint 1: <the kind of test or check that verifies it — in words, never a file path>

## More information

- Revisit when: <the condition that reopens this decision>
- Evidence: <links to spikes, measurements, discussions>

## Implementation log

(Append only. Records only how open items in this decision were settled.)
```

Required sections: *Context and problem*, *Decision drivers*, *Considered options*, *Decision outcome*, *Consequences*, *More information* (with a non-empty *Revisit when*). *Confirmation* is required whenever *Constraints* exists. *Constraints*, *Pros and cons* and *Implementation log* are optional. `verify-decision-format` checks exactly this list.

How much to write:

- **Decision outcome** is long enough when a reader of the outcome and constraints alone can tell whether an implementation violates the decision. Past a dozen points it usually holds implementation detail (→ module README) or two decisions (→ split). Protocol formats and other design detail go in a design doc or module README, linked from here.
- **Constraints** are optional; when present they are numbered, and *Confirmation* says how each one is verified.
- **Considered options** must judge each option against the drivers. Add a separate *Pros and cons* section when the options need it.

Scopes: <<the scope list from the interview, e.g. domain, storage, auth, toolchain>>. A new scope is added here and in the gate's configuration in the same PR.

## Status and relations

| Status | Meaning |
| --- | --- |
| proposed | Under discussion; edit freely |
| accepted | In force; set when the PR that adopts it merges |
| rejected | Considered and declined; kept so the same idea is not re-proposed |
| deprecated | No longer applies and nothing replaces it; add one dated line saying why |
| superseded | Wholly replaced by another record |

*Relations* is a list separated by `; `, each item one of (`<ref>` is a slug, or `ADR-NNNN` for a legacy record):

- `depends on <ref>`
- `supersedes <ref>`, or `supersedes <ref>: <which part>` for part of it
- `superseded by <ref>` (status `superseded`), or `<which part> superseded by <ref>` (status stays `accepted`)

Both sides of a supersession are written; `verify-decision-format` checks that they agree.

## After acceptance

Only these may change in an accepted record: the *Status* and *Relations* lines, broken links, typos, and new lines appended to *Implementation log*. Anything else needs the `decision-amend` PR label and a reason (`verify-decision-immutable`).

| Situation | What to do |
| --- | --- |
| A PR that implements the decision as written, a refactor, a bug fix | Leave the record alone |
| An item the record left open is settled | Append a dated line to *Implementation log*: what was settled, which PR |
| The implementation contradicts the outcome or a constraint | In the same PR, a new record that supersedes it, wholly or in part |
| Implementation is complete | Nothing to write; the index derives it from tags |

The test: *would someone reading only the original outcome and constraints build the wrong thing?* If yes, supersede; if no, leave it or append to the log.

## Implementation status

A test or verify script that confirms numbered constraint *n* of a record carries `[decision:<slug>#<n>]` in its title. The index counts covered constraints per record. Records never link to tests, so renaming or moving a test changes nothing here; deleting the last test for a constraint lowers the count in that PR's generated index, where review sees it. `verify-decision-tags` rejects tags that name no record or no constraint. Tests under <<prototype or spike directories>> do not count: a spike shows a decision is feasible, not that the product implements it.

## Where other things live

| Information | Home |
| --- | --- |
| Why A over B | This folder |
| How an open item was settled | The record's *Implementation log* |
| What holds today | [architecture.md → Current decisions](../architecture.md#current-decisions) |
| Module interfaces, invariants, accepted limitations | Module READMEs |
| Measurements and test evidence | <<evidence location>> |
| Whether a product requirement is met | <<acceptance list, if the repo has one>> |
| Why one change was made | Commit message and PR description |
| An escaped bug | [../postmortem/](../postmortem/README.md) |

## Linking

- A module README's *Decisions* section lists the records that shape it, by slug; its *Invariants* restate the constraints it must uphold and link the record.
- Code that looks odd because of a decision carries a one-line comment naming the slug.

## Notes for the generator

- Do not write decision records during initialization unless the survey surfaced a decision the user confirms (e.g. "we deliberately don't use an ORM"). An empty, well-formed folder with an empty generated index is the correct starting state.
- Write the README in the language the user writes decisions in. The *Status and relations* table and the *Required sections* line are the gate's configuration source: header field names, status values, required headings and relation keywords in `verify-decision-format` must match them word for word. Translate them only together with that configuration.
- If the repo already has decision records (`docs/adr/`, `docs/architecture/decisions/`, MADR files): keep their directory, freeze their bodies, keep their names, and migrate only their headers to the five fields — one PR with the `decision-amend` label, the old status text kept as a quoted note. Records numbered after that point use dated names. Tell the user which existing records already supersede each other and write those relations.
- Add the *Current decisions* section to `docs/architecture.md` at the same time (`templates/architecture.md`).
- The generated index needs markers the generator replaces between; keep them when editing the README.
